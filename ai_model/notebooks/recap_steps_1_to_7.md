# Project Summary — Resume Ranking

## Project Objective

Predict `matched_score` (a score between 0 and 1) that measures how well a resume matches a job posting, from a dataset of 9,544 rows (Resume Data for Ranking).

Complete project roadmap:
`1. Understand the dataset → 2. EDA → 3. Cleaning → 4. Features → 5. Ridge → 6. Random Forest → 7. Gradient Boosting → 8. Cross-validation → 9. Model selection → 10. sklearn Pipeline → 11. Save → 12. API`

---

## Steps 1-2 — Understand the dataset & EDA

### What we discovered

- **9,544 rows, 35 columns**, no exact duplicates, no score values outside [0, 1].
- **Structuring discovery**: the dataset is not 9,544 independent real applications, but **340 unique resumes crossed with 28 positions** (almost Cartesian product: 340 × 28 ≈ 9,520, very close to the actual 9,544 rows). Each resume therefore appears ~28 times, with a different score each time depending on the targeted position.
- **Direct and critical consequence**: a classic random train/test split would cause data leakage (the same resume ending up in both train and test). → **Decision: mandatory split by resume group** (`GroupShuffleSplit`), applied from step 4 onwards.
- The `matched_score` has a **discrete stepwise distribution** (only 229 distinct values, clear peaks at 0.33/0.65/0.85...) → probably generated by a formula/algorithm rather than freely assigned.
- **`job_position_name` is strongly correlated with the score**: median ~0.45 for physical engineering positions (Civil Engineer, Mechanical Designer...) vs ~0.80 for tech positions (Machine Learning Engineer, DBA...). This is a **structural bias of the dataset** that we then found in all models.
- **No link between text length and score** (number of skills, length of `career_objective`) → text volume is not a useful signal.
- **The skill overlap resume ↔ position (`skills_overlap`) is positively correlated with the score**, but remains low in raw value (~95% of rows with overlap = 0) due to too strict text matching.
- **Structured missing values by blocks** (e.g., all certification columns are missing together) → these are unfilled resume sections, not collection errors (structural MNAR), so no statistical imputation needed.

## Step 3 — Text cleaning

File: `02_data_cleaning.ipynb` → output `data/processed/resume_data_clean.csv` (9,544 rows, 43 columns), tracked with DVC.

### Decisions made and justification

| Action | Why |
|---|---|
| Aggressive free text cleaning (lowercase, punctuation removed) for `career_objective`, `responsibilities`, etc. | Prepare for vectorization (TF-IDF) |
| **Light** skill cleaning (`normalize_skill`): lowercase + spaces, without removing technical punctuation | Avoid breaking terms like `C++`, `.NET` |
| Recalculation of `skills_overlap` after normalization | Verify the gain of cleaning on matching |
| Replacement of NaN text by empty string (no statistical imputation) | Missing values are unfilled resume sections, not errors |
| Addition of binary indicators `has_xxx` (has_certifications, has_languages...) before losing the info | The absence of a section can be informative in itself |
| Removal of columns >90% empty (`address`, `languages`, `proficiency_levels`, etc.) | Too sparse to provide a reliable signal |

## Step 4 — Feature engineering

File: `03_feature_engineering.ipynb` → outputs `X_train.npz`, `X_test.npz`, `y_train.npy`, `y_test.npy`, `tfidf_vectorizer.pkl`, `job_position_encoder.pkl`.

### What was built

1. **Train/test split by resume** (`GroupShuffleSplit`, grouped on `skills`, with NaN handling via a unique identifier per row) — 0 resumes in common verified between train and test.
2. **TF-IDF** (200 words max, unigrams + bigrams) trained **only on train**, applied separately to resume text (`resume_text`) and job text (`job_text`), with a shared vocabulary to allow comparison.
3. **`text_similarity`**: cosine similarity between the TF-IDF vector of the resume and that of the job — feature designed to replace the raw `skills_overlap`, too strict.
4. **One-hot encoding of `job_position_name`**, with `handle_unknown="ignore"` to not crash when facing a position never seen in production.
5. **Numeric features preserved**: `skills_overlap`, `experience_years_min`, all `has_xxx` flags.
6. **Final matrix `X`**: ~438 columns (200 + 200 TF-IDF + 1 similarity + 9 numeric + ~28 categorical one-hot).

### Vigilance point retained

Always **fit encoder/vectorizer on train only**, never on the whole dataset — otherwise data leakage via learned vocabulary, same rule as for the split.

## Steps 5-7 — First models

### Compared results

| Metric | Ridge (baseline) | Random Forest | Gradient Boosting |
|---|---|---|---|
| MSE | 0.0247 | **0.0171** | 0.0182 |
| MAE | 0.1227 | **0.0983** | 0.1036 |
| R² | 0.2067 | **0.4513** | 0.4155 |

**Random Forest is the best of the three on this split**, Gradient Boosting just behind, Ridge significantly weaker (but remains a useful baseline — it confirms there is a real signal in the data, not just noise).

### What we learned from each model

- **Ridge**: confirms that `text_similarity` is the most useful feature for predicting a high score. Shows a marked "regression to the mean" effect (over-predicts low scores, under-predicts high scores) — typical behavior of a regularized linear model.
- **Random Forest**: better overall performance, less marked regression to the mean effect.
- **Gradient Boosting**: performance close to Random Forest but slightly lower — probably because the dataset (340 unique resumes) is too small/low-variety for GB to fully exploit its capacity for progressive error correction.

### A bias that appears in all 3 models

The words `autocad`, `civil engineering`, `mechanical engineering` **lower** the prediction in all models, while `text_similarity` remains always in the top of important features. Interpretation: the model learns partly the **true matching signal** (`text_similarity`), but also a **shortcut linked to the structural bias position ↔ score** identified from the EDA (physical engineering positions have lower scores in this dataset, independently of actual matching quality).

**This is not a code error** — it's a limitation of the dataset (closed structure with 28 positions, with a scoring bias between categories) to keep in mind for the final model choice (step 9).

## Open decisions / tracks for later (not now)

- **More data** (more varied resumes, more sectors) could reduce the position ↔ score bias and improve generalization — to consider only once the complete pipeline is finished (step 12), not before.
- **Pre-trained embeddings** (Hugging Face `sentence-transformers`, without finetuning) as alternative/complement to TF-IDF, to test once a reference model runs well.
- **Finetuning a language model (BERT...)**: ruled out for now, too risky (overfitting) with only 340 unique resumes. To reconsider with a richer dataset.
