# EDA Synthesis — Resume Ranking Dataset

> Human reference document: this file summarizes and **interprets** all results obtained in `01_dataset_exploration.ipynb` (steps 1 and 2), with decisions to take for step 3 (text cleaning) and their justification.

---

## 1. Dataset overview

- **9,544 rows**, **35 columns**
- **0 exact duplicate** (no row strictly identical to another)
- The target to predict is `matched_score`, a continuous score between **0 and 0.97** (mean 0.66, median 0.68)

**What this means concretely**: the dataset is clean in the strict sense (no duplicate rows, no aberrant values like negative score or > 1). But "no exact duplicates" doesn't mean "no repetition" — see point 2.

---

## 2. Key discovery: this is not 9,544 different resumes

By counting unique values of the `skills` column, we find only **340 distinct resumes**, while the job posting (`job_position_name`) counts **28 distinct positions**.

By crossing several profile columns (`career_objective`, `skills`, `educational_institution_name`, `degree_names`, `professional_company_names`, `positions`), we find **344 unique combinations** — a figure very close to 340. This confirms that the `skills` column alone is almost sufficient to identify a resume.

And if we look at the frequency of positions (`job_position_name`), each position appears approximately **341 to 342 times**.

**Interpretation**: 340 resumes × 28 positions ≈ 9,520, which is very close to the actual 9,544 rows. **This dataset is therefore not a collection of real applications, but a (almost complete) Cartesian product: each resume was evaluated against (almost) each job posting.** This is not a defect of the dataset, but it must absolutely be kept in mind:

- **The same resume appears ~28 times**, with a different score each time depending on the targeted position.
- The score therefore depends on the **pair (resume, position)**, not the resume alone.

### Why this is important for the future

If we do a classic random train/test split (`train_test_split` line by line), **the same resume will end up in both train and test** (just evaluated against a different position). The model can then "recognize" a resume it already saw in training → too optimistic validation score, which doesn't reflect true performance on a completely unknown resume.

**Decision for the future**: use a **grouped split by resume** (`GroupShuffleSplit` or `GroupKFold` from scikit-learn, with `groups = df["skills"]` or a dedicated resume identifier), to guarantee that a given resume never appears in both train and test.

---

## 3. Score distribution (`matched_score`)

![histogram](attachment) *(see cell 18 of the notebook)*

The histogram is **not a smooth curve**: we see clear peaks at certain precise values (around 0.33, 0.65, 0.85...), with only **229 distinct values** over 9,544 rows, and certain values that recur very often (`0.85` appears 1,470 times, `0.65` appears 1,321 times).

**Interpretation**: the score was probably not assigned "manually" or in a purely continuous way, but generated by a **formula/algorithm** combining a small number of discrete criteria (e.g., number of skills in common, correspondence of experience level, etc.), which naturally produces recurring values.

**Decision for the future**: this is not a problem in itself for a regression model, but it means we could potentially reconstruct part of the scoring logic via feature engineering (see point 5). It's also worth keeping this info in mind for model evaluation: don't expect a "randomly noisy" signal but rather a fairly structured function.

---

## 4. Average score by position

The median score varies strongly depending on the targeted position: from **~0.45** for positions like *Site Engineer*, *Mechanical Designer*, *Civil Engineer*, up to **~0.80** for technical positions like *Machine Learning Engineer*, *Database Administrator*, *AI Engineer*, *Full Stack Developer*.

**Interpretation**: either the resumes in the dataset are globally more oriented "tech/data" and therefore match better with tech positions, or the scoring algorithm is structurally more generous on these positions. In both cases, **`job_position_name` is a very informative variable** to predict the score.

**Decision for the future**: encode `job_position_name` as a categorical feature (one-hot or target encoding) — it's a strong candidate, not just a context variable.

---

## 5. Text length vs score: no visible correlation

By plotting `matched_score` as a function of the number of listed skills (`skills_count`) and the length of the text `career_objective`, **no clear trend emerges** — the point cloud is flat, with just the same horizontal bands due to discrete score values (point 3).

**Interpretation**: having a more "filled" resume (more words, more listed skills) doesn't mechanically increase the score. This is rather reassuring: it means the score probably reflects a true **relevance** logic (correspondence to the position) rather than a simple text volume effect.

**Decision for the future**: don't rely on "raw text length" type features as main predictors. They can be kept as secondary features, but the effort must focus on **matching** features (point 6).

---

## 6. Skill overlap (`skills_overlap`): the clearest signal found so far

By calculating the number of common skills (raw text, lowercase) between `skills` (resume) and `skills_required` (position), we observe a **true increasing trend**:

| Common skills | Approximate median score |
|---|---|
| 0 | ~0.68 |
| 1 | ~0.75 |
| 2 | ~0.78 |
| 3 | ~0.89 |

**Interpretation**: this is the variable most clearly correlated with the score found during the EDA. But note that the **vast majority of rows have an overlap of 0**, while intuitively many resumes should share at least one skill with the targeted position. This is probably because the comparison is made on raw text strings (e.g., `"Python"` vs `"python programming"` don't match even though it's the same skill).

**Decision for the future (directly justifies step 3)**: text cleaning must include **strong normalization** of skills (lowercase, punctuation removal, handling of common synonyms/abbreviations) before recalculating this overlap — otherwise we largely underestimate the true matching. This `skills_overlap` feature (once the text is well cleaned) will probably be one of the most important features of the final model.

## 7. Missing values: structured, not random

| Column | % missing |
|---|---|
| `languages`, `proficiency_levels` | 92.7% |
| `address` | 91.8% |
| `issue_dates`, `certification_skills`, `certification_providers`, `expiry_dates`, `online_links` | 79.0% |
| `extra_curricular_*` (4 columns) | 64.1% |
| `career_objective` | 50.3% |
| `age_requirement` | 42.8% |
| `skills_required` | 17.8% |
| `experiencere_requirement` | 14.3% |
| Education columns (`degree_names`, `passing_years`, etc.) | 0.9% |
| `skills` | 0.6% |
| `job_position_name`, `responsibilities`, `responsibilities.1`, `educationaL_requirements`, `matched_score` | 0% |

The heatmap of missing values (cell 22) shows that these columns are missing **in coherent blocks**: when `certification_providers` is missing, `certification_skills`, `online_links`, `issue_dates` and `expiry_dates` are also missing (same for the "extra-curricular activities" block and the "languages" block).

**Interpretation**: these are not data collection errors. These are **optional resume sections that the candidate simply didn't fill** (not everyone has certifications, not everyone listed spoken languages). This is what we call **structural MNAR** (Missing Not At Random, but in a predictable and logical way).

**Decision for the future**: don't try to statistically impute these values (mean, mode, etc.) — it would make no sense to "guess" a missing certification. Instead:
- Replace missing texts by an empty string `""` (no loss of info, the NLP model will naturally treat this as "nothing to say").
- Consider adding a binary indicator like `has_certification`, `has_languages` — the *absence* of a section can itself be informative.
- Columns with >90% empty (`address`, `languages`, `proficiency_levels`) are probably to **exclude** from the model: too sparse to provide a reliable signal.

---

## 8. Required experience vs score: weak signal

By grouping the score by minimum years of experience required (`experiencere_requirement` parsed), medians remain close to each other (0.58 to 0.75 depending on the level), without a clear monotonic trend. There's a bit more variance/low values for high levels (5 and 15 years), but nothing as clear as the skill overlap (point 6).

**Interpretation**: required experience alone doesn't explain much of the score. It may play a role in interaction with other criteria, but not as an isolated variable.

**Decision for the future**: keep this feature (it costs nothing to extract) but don't expect much from it — it probably won't be in the top of important features.

---

## 9. Synthesis — What we retain for step 3

| # | EDA finding | Decision for step 3 / future | Why |
|---|---|---|---|
| 1 | 340 resumes reused ~28 times each | Train/test split **by resume** (`GroupShuffleSplit`) | Avoid data leakage (same resume in train and test) |
| 2 | Discrete score, generated by formula | No cleaning action, but keep in mind for model evaluation | The signal is structured, not randomly noisy |
| 3 | `job_position_name` very correlated with score | Encode as strong categorical feature | Key variable identified from EDA |
| 4 | No link text length / score | Don't rely on raw length features | Text volume doesn't reflect relevance |
| 5 | `skills_overlap` correlated with score, but underestimated by raw text matching | **Priority #1 of cleaning**: normalize skills (lowercase, punctuation, synonyms) for better matching | It's the strongest signal found, but limited by current text quality |
| 6 | Structured missing values by blocks (unfilled resume sections) | Replace by empty string + add `has_xxx` indicators; exclude columns >90% empty (`address`, `languages`, `proficiency_levels`) | These are logical absences, not errors — absence can be informative |
| 7 | Required experience: weak signal | Keep the feature but low priority | Little isolated explanatory power |

**Conclusion**: step 3 (text cleaning) must focus in priority on:
1. Normalization of skill columns (`skills`, `skills_required`) to make the `skills_overlap` calculation reliable.
2. Standard cleaning of free texts (`career_objective`, `responsibilities`, `responsibilities.1`): lowercase, removal of parasite characters, handling of `\n`.
3. Explicit handling of missing values (empty string + binary indicators), without statistical imputation.
4. Setting up the resume split logic from now, so that all subsequent steps (features, models) are built on a healthy foundation.
